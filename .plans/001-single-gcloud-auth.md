## Overview

`gcloud_setup()` signs in twice: `gcloud auth login` (the student
account, what gcloud itself uses) and then `gcloud auth
application-default login` (ADC, what terraform authenticates with).
Both go through the same browser, the same account, and the same
"click Allow" moment - twice. `gcloud auth login --update-adc` writes
the student credentials to both stores in one browser flow.

## Motivation

### Current State

```python
# lab-start, gcloud_setup() (~line 840)
if subprocess.run(["gcloud", "auth", "login"]).returncode != 0:
    print(f"{YLW}login did not complete - skipping gcloud setup{RST}")
    return False
# ... three config set calls ...
print(f"\n{CYN}Application-default credentials: one more browser sign-in.{RST}\n")
if subprocess.run(["gcloud", "auth", "application-default", "login"]).returncode != 0:
    print(f"{YLW}ADC login did not complete - terraform may not authenticate{RST}")
    return False
```

This creates problems:

1. **Two browser flows for one identity**: the student signs in with
   the same Qwiklabs account twice, back to back. The second flow is
   pure ceremony - same browser, same account, same consent screen.
2. **A partial state that lies**: if the second login is cancelled,
   gcloud works but terraform doesn't, and the function returns False
   after the config was already set. One flow makes the state atomic:
   both stores are written or neither is.
3. **Two failure messages to keep honest**: "login did not complete"
   and "ADC login did not complete - terraform may not authenticate"
   describe the same user mistake twice.

### Desired State

```
$ ./lab-start my-lab
...
? Authenticate gcloud now? [y]:
A browser window will open - sign in with the lab credentials, then come back here.
  (one flow: gcloud + application-default credentials)
  ... browser once ...
  setting gcloud project ...
  setting gcloud region ...
  setting gcloud zone ...
  gcloud:    ok
  authenticated as student-xx-xxxx@qwiklab.net
```

## Research Findings

### What `--update-adc` actually does (docs, checked 2026-11-01)

From the `gcloud auth login` reference (page dated 2026-05-27):

> Write the obtained credentials to the well-known location for
> Application Default Credentials (ADC). ... Any credentials
> previously generated by `gcloud auth application-default login`
> will be overwritten.

**Key finding**: the current reference carries **no scope caveat** on
`--update-adc`. The caveat the roadmap remembers ("credentials from
`--update-adc` don't carry the same scopes as ADC-login credentials;
some APIs, e.g. Dialogflow, need `userinfo.email`") was in older
versions of that page and is gone. What remains verifiable:

| Store | Written by | File |
| ----- | ---------- | ---- |
| gcloud's own credentials | `auth login` (unchanged) | `~/.config/gcloud/credentials.db` |
| ADC | `--update-adc`, same flow | `~/.config/gcloud/application_default_credentials.json` |

**Implication for lab-reset**: the two stores stay two separate
files. `gcloud auth application-default revoke --quiet` and
`gcloud auth revoke <account> --quiet` (lab-reset, lines 199-218)
remain exactly correct - one flow wrote two files, two revokes
remove two files. **lab-reset needs no change.**

### What terraform needs from ADC

- The terraform google provider requests the
  `https://www.googleapis.com/auth/cloud-platform` scope against
  user credentials - which is also in `gcloud auth login`'s scope
  set, and in the documented ADC-login defaults (the
  `application-default login` reference lists `openid`,
  `userinfo.email`, `cloud-platform`, `sqlservice.login`).
- The google provider takes its project from the provider
  config/tfvars, not from ADC - so the one behavioral difference
  worth watching (see Open Questions 2) is the **quota project**:
  `application-default login` writes one from gcloud's context;
  the `--update-adc` docs say nothing about quota projects.

**Key finding**: no documented gap between what `--update-adc`
writes and what terraform reads. The residual risk is undocumented
behavior, not documented incompatibility - which is exactly why
the roadmap makes the real-lab terraform run a **Release**
criterion, not a Plan assumption.

### What the tests already pin down

- `tests/util.py` stubs gcloud: every invocation is logged to
  `$GCLOUD_LOG`, exit 0. `gcloud_setup()` has never been under
  test (existing runs all pass `--skip-auth`) - the red test for
  this item is its first.
- `tests/test_refresh_cli.py` (line 62) asserts the *reset* side:
  `auth application-default revoke --quiet` in the log. That
  assertion must keep passing untouched - proof the reset still
  revokes both stores after the change.

## Design Decisions

| Decision | Choice | Rationale |
| -------- | ------ | --------- |
| login command | `gcloud auth login --update-adc` | one browser flow writes both stores; documented to overwrite prior ADC |
| second ADC login | removed | same account, same browser, same consent - the flow adds nothing |
| config set order | unchanged (after login) | `--update-adc` writes ADC during login; the provider's project comes from tfvars, so config timing against ADC is irrelevant |
| failure path | existing returncode check | a cancelled browser flow or an old gcloud that lacks the flag both land in "login did not complete" - no version sniffing |
| lab-reset | no change | two files were written by one flow; two revokes still remove both; its tests stay green untouched |
| user messages | rewritten | one sign-in message; "one more browser sign-in" line deleted |
| scope caveat | verified at Release, not assumed | docs no longer carry it; the real-lab terraform run is the evidence the roadmap demands |

## Architecture

```
before:
  browser login (auth login) ──> config set x3 ──> browser login (ADC login)
                                                        │ cancel = half-state

after:
  browser login (auth login --update-adc) ──> config set x3
       │
       ├─ writes gcloud credentials.db
       └─ writes application_default_credentials.json   (one flow, both stores)

lab-reset (unchanged, still correct):
  auth application-default revoke --quiet   ──> removes ADC file
  auth revoke <account> --quiet             ──> removes gcloud credential
```

## Edge Cases

### gcloud too old to know `--update-adc`

1. the flag has existed since ~2020; a managed lab machine has a
   modern gcloud
2. if not, the command exits non-zero and the existing
   "login did not complete" path handles it - loud failure, no
   fallback machinery

### ADC still holds a previous lab's credentials

1. `--update-adc` overwrites them (documented)
2. desired anyway: each Qwiklabs lab is a fresh student account;
   stale ADC from the last lab is precisely what must not survive

### Browser flow cancelled halfway

1. gcloud exits non-zero, `gcloud_setup()` returns False before
   any config set runs
2. both-or-neither - strictly better than today, where cancelling
   the second login left config set and gcloud credentialed but
   terraform unable to authenticate

### The quota project in ADC

1. `application-default login` writes one from gcloud context;
   `--update-adc` writes ADC *before* `config set project` runs,
   so a quota project (if written at all) may be stale or absent
2. terraform's provider takes its project from tfvars; the student
   account owns the lab project. Check the ADC file on the real
   run (Phase 3.2), but no code change is expected to hinge on it

## Open Questions

All three settled. 1 and 2 at Release, on the real lab
(landing-zone-challenge, 2026-11-01); 3 by implementation.

1. **Does the documented-scope risk survive in practice?**
   - Current `--update-adc` docs carry no caveat (verified
     2026-11-01); the roadmap's Release criterion is the
     real-world check.
   - **Settled**: no caveat in the docs, none in practice.
     tokeninfo on the ADC access token shows
     `https://www.googleapis.com/auth/cloud-platform` granted -
     a superset of the documented ADC-login defaults (openid,
     userinfo.email, cloud-platform, sqlservice.login) plus
     gcloud's own set (appengine.admin, compute, ...). A
     minimal terraform config with the google provider read
     `data.google_project` against the live project through
     ADC alone (`Read complete after 1s`, real project number
     returned). The one-line revert was never needed.

2. **Quota project written by `--update-adc`?**
   - Options: (a) inspect
     `~/.config/gcloud/application_default_credentials.json`
     after the real run and record what's there, (b) ignore it
   - **Settled**: (a) - `--update-adc` writes **no**
     `quota_project_id` (keys: account, client_id,
     client_secret, refresh_token, type, universe_domain;
     `application-default login` would have added one from
     gcloud context). And it doesn't matter: the provider takes
     its project from tfvars, and the plan authenticated
     without one. No code change, as predicted.

3. **Keep a two-login fallback for old gcloud?**
   - **Settled**: no - one code path, no version sniffing;
   an unsupported flag fails loudly through the existing path,
   and the failure message already tells the user what was
   skipped. Shipped that way.

### Release note on the evidence

The lab's own full-config `terraform plan` could not run: the
`shared-vpc` module in `task1.tf` is populated *at apply time*
by a `null_resource` that rsyncs the module out of the lab's GCS
bucket, so plan dies with "Module not installed" before any
provider call. That is the lab's design, not an auth problem.
The acceptance evidence is therefore a minimal google-provider
config in a throwaway dir: same provider, same ADC, same live
project, real authenticated read.
